# Contract errors

After Foundation core#711, document lookup answers `InvalidParameterFormat` when `data` is not a JSON object, or when an identifier key is an object, an array, `null`, or a number where text is expected. Several wrong values come back as one `MultipleErrors`. A missing or empty key stays `MissingParameter`. Entry numbers still accept numbers.

Document types that resolve an identifier list these error codes:

- `InvalidParameterFormat` on `data`
- `InvalidParameterFormat` on the identifier key
- one `MultipleErrors` entry

This applies to the eleven transfer-order and assembly-order lookups listed in #27. It does not change Item range readers, document creation, undo or reservation readers. Test codeunit 96922 checks the public errors chapters; 96923 exercises strict malformed data/identifiers and aggregation through the public dispatcher. Foundation 28.0.2.0 is the minimum dependency. Runtime results are recorded separately from test source.

## Native tracking/reservation candidate (#5/#7/#36/#37)

`Inventory.Tracking.Get` reads a line identified by `source: {type, systemId}`; sales/purchase/transfer also accept `documentType` plus `documentNo`/`lineNo`, `documentType` plus `systemId`, or the line SystemId as subject. Qualified document types are `Sales.Order`, `Sales.Invoice`, `Sales.CreditMemo`, `Sales.ReturnOrder`, corresponding `Purchase.*` values, and `Transfer.Order`. Unqualified `Order` remains the legacy sales selector. Transfers default to Outbound and accept `transferDirection: Inbound`. Item reads retain Foundation item lookup (`subject`, `itemNo`, `itemId`, `id`, `systemId`, `recordSystemId`).

The response identifies each row as `ReservationEntry`, `TrackingSpecification` or `ItemLedgerEntry`. Source pointers include the stable `sourceType` name, numeric `sourceTableNo`/`sourceSubtype`, document number, batch, production line and reference line; reservation-pair sides are distinguished by `positive`. Pending tracking and posted handling are separate records. Quantities are base units. No persistent tracking, reservation or ledger record is written by a read.

Exact `lotNo`, `serialNo`, `packageNo`, `variantCode`, `locationCode` values may include blank. `locationFilter` accepts BC filter syntax and intersects `locationCode`. `skip` is nonnegative; `take` is 1..10000, default 100. `noOfLines` counts returned rows; `totalNoOfLines` counts matching rows before paging. An empty tracking set returns `RecordNotFound`; a page beyond the end of a nonempty set returns an empty successful page.

`Inventory.TrackingAvailability.Get` returns `availability`, grouped by lot/serial/package, location and variant, with `inventory`, `qtyReserved` and `availableQuantity`. Reserved quantities come from each posted entry's native `Reserved Quantity` FlowField. Only open positive item ledger positions contribute. The binding [Architect AC-5 withdrawal and reinstatement](https://bifrst-group.slack.com/archives/C0C0XM70YF8/p1791931218380149) uses the entry's native expiration only when the Item Tracking Code has Use Expiration Dates enabled. Disabled or undated entries return blank; grouped lot/package disagreement returns blank. Master precedence was struck from AC-5 on 13 October because the BC 28.5 target has no such Lot/Package master field. No table extension is introduced. See [expiration acceptance](inventory-expiration-acceptance.md) for provenance.

`Inventory.Reservation.Get` accepts the same document/source forms, item identifiers, `entryNo` and tracking/location filters. All supplied criteria intersect before entry-not-found is evaluated. An entry number identifies a native reservation pair; supply/demand rows are distinguished by source and positive, rather than silently discarding one side.

Create accepts a native source object or legacy document keys. Supply is either an explicit `supply` object or `itemLedgerEntryNo`; specifying both is refused. Omitting both requests matching posted inventory, allocated in entry order through native Create Reserv. Entry adapters after whole-quantity availability checks. No AutoReserve is used. The response includes `quantityBase` and the resulting `entryNo` or `entryNos`. Requested tracking must match a selected ledger entry; serial allocations are one base unit. Quantity input uses the source UOM. Cancel accepts document/source keys or entry number and preserves native paired cancellation. Both Create and Cancel refuse a source with no native outstanding quantity. An open, unreserved source still cancels idempotently. Cancel returns `entriesCancelled`, `itemNo`, `quantityUnreserved` in source units and `quantityBaseUnreserved` in base units. W1 permits reservation pairs on transfer journal lines; ordinary adjustment journal sources retain the native refusal without partial writes.

These are implementation contracts, not a claim of full issue acceptance. Complete source scenarios, restricted permissions, concurrent writes, UI/MCP and external dependencies remain tracked in the worker-8 acceptance matrix. No older “done on main” sentence above supersedes current evidence.


## Current retained costing implementation (#4, #35)

This source supersedes the historical costing snapshot above; it does not mark either issue complete.

- `Inventory.Price.Update` selects exactly one Item through Foundation subject/identifier/named-field tableView rules. It requires `unitPrice` (number or invariant decimal string), refuses unsupported fields, checks native Item/Unit Price field permissions and requires explicit `allowBlocked` for blocked Items. Native Validate/Modify executes in the outer write transaction or an isolated Codeunit.Run; subscriber failures roll back. Response includes actual previous and resulting unit price.
- `Inventory.Revaluation.Calculate` runs native report 5899 into an explicitly identified **empty Revaluation batch**. Required `postingDate` and output `documentNo`; optional native item/location/variant filters, `calculatePer` (`Item Ledger Entry` or `Item`) and per-item `byLocation`/`byVariant`. It does not post or update Standard Cost. Returns actual created-line counts and calculated/revalued totals. Unsupported options refuse before execution.
- `Inventory.Revaluation.Post` and `Inventory.Revaluation.PreviewPost` identify the batch by subject `TEMPLATE|BATCH`/SystemId or data `templateName`/`batchName`/SystemId aliases. Both require a Revaluation template, native journal permissions and the posting gate. Post suppresses inner commits and returns the real native Item Register range. Preview uses BC posting preview and the public Foundation serializer, with captured `preview[]`, `totals` and rollback; journal counts alone are not preview evidence.
- Report 795 accepts its native item/category filters and itemByItem/postToGL options. Reports1002/1003 use their actual pending-entry item/date selection; documentNo is an output option. Native report1003 refusal with mandatory journal templates remains a documented pending configuration gap.

Current delivery still requires zero-warning compilation/publication, current-tip full-suite/UI/licensed self-seeded MCP, reviewed evidence and cleanup. The four foreign permission warnings, Foundation DomainDisabled and licensed runtime #95 remain tracked. Source and native AL checks alone do not establish complete shipping workflow acceptance; external HelpLinks/documentation remains Tryggvi's #31 scope.

## Native journal candidate (#6, #34)

Reclassification Check now runs Item Jnl.-Check Line and returns `validationResult` (Ready, ReadyWithWarnings or NotReady), errors and warnings. PreviewPost runs native posting preview and serializes captured ledger impact. Post runs Item Jnl.-Post Batch in an isolated process with inner commits suppressed. Each requires an existing nonrecurring Transfer template batch. `templateName`/`batchName`, legacy `journalTemplateName`/`journalBatchName`, or subject `TEMPLATE|BATCH`/batch SystemId identify the batch; conflicting identifiers are refused. Optional `lineSystemIds` must be a nonempty, duplicate-free array entirely within that batch. Post returns actual `itemRegisterNo`, entry ranges, `postedLineCount` and per-line `result`; unselected lines remain untouched.

Physical inventory adds registered Check, PreviewPost and RecordCount, retaining the existing Calculate/Post/Record identities. All use an existing nonrecurring Phys. Inventory template batch. Calculate invokes report 790, requires an empty batch plus `postingDate` and `documentNo`, and supports native item/location/variant filters and `itemsNotOnInventory`/`includeItemsWithNoTransactions`. RecordCount accepts `counts: [{lineNo|systemId, qtyCounted?}]`, validates the full selection and uses native Validate/Modify inside the process transaction. Omitted qtyCounted leaves the line unchanged and returns counted=false; explicit zero records zero. Duplicate or foreign line IDs and invalid quantities are refused. Legacy Record accepts its existing lineNo/quantity input and keeps its response fields. Preview captures native rollback entries; Post returns item and physical inventory ledger ranges from the actual register. Post/Preview use Foundation's published ItemJournal.Post IsEnabled interface to enforce its existing native journal/ItemPost gate. No private gate object or new token is used.

The [Architect reconciliation of #6 AC8/9](https://github.com/businesscentralal/bc-origo-bifrost-inventory/issues/6#issuecomment-6160056699) confirms the later field-granularity decision in #4: generic Item Journal Line writes stay legal and there is no table-83 write-restriction subscriber. Existing governed Item cost/price field restrictions remain unchanged. This reconciles the acceptance contract; it is not a licensed Data.Records.Set test pass. Shipping licensed MCP, full workflow UI and exact-tip readiness remain separate from native helper tests; #95 is not waived.

## Native undo and application candidate (#39, #40)

Transfer UndoShipment uses BC 28.5's codeunit 9030 `Undo Transfer Shipment`. `documentNo` is required; optional `lineNos` is a nonempty, distinct set of original shipment lines. All selected lines must still have an unreceived native transfer line. Native corrections preserve unselected lines. Assembly UndoPost uses `Assembly-Post.Undo` with optional `recreateOrder` (default false), returns the observed recreated-order state, and refuses already reversed or consumed output through native validation. Both write operations use the caller's Omit Commit policy and suppress internal commits inside the process. Transfer UndoReceipt remains explicitly unsupported: no corresponding native W1 API was established. It requires an Architect platform/acceptance disposition, not a direct posted-row workaround.

ItemApplication.Get requires exactly one of `itemNo` and `itemLedgerEntryNo`. Optional `locationCode` and `variantCode` are exact filters on the selected ledger entries. Results deduplicate native application entries connected on either side and include `inboundEntry` and `outboundEntry` projections. Origin applications can have outbound entry zero; the projection explicitly reports `exists=false`. No query writes application or ledger data.

ItemApplication.Unapply requires `itemLedgerEntryNo` and unapplies all real connected applications through `Item Jnl.-Post Line.UnApply`, with native worksheet logging and adjustment flags. Legacy `entryNo` retains its original application-entry meaning; it cannot be mixed with the ledger selector. Empty selection and native period, transfer, correction and other worksheet refusals fail atomically.

ItemApplication.Reapply requires `outboundEntryNo`, `inboundEntryNo`, and positive `quantity` in base units. Entries must have opposite correct signs, matching item/location/variant and sufficient unreserved remaining quantity. A manually bound, pair-scoped public native integration event caps the applied quantity; native posting remains responsible for all application and ledger writes. Actual resulting remaining quantities must change by exactly the requested quantity or the whole operation fails. Legacy `itemLedgerEntryNo`/`applyToEntryNo` aliases remain supported with their full available quantity default; mixed alias sets are refused. Both operations mark adjustment required without running Adjust Cost. They keep the native noninteractive default: no interactive worksheet crash-recovery markers are created, so a later worksheet open cannot silently complete an explicitly partial API result through crash recovery.

Native AL acceptance and native Web Client checks do not substitute for licensed shipping message/MCP verification. Structured error-code completion still depends on Foundation's DomainDisabled contract. All affected types remain subject to current-tip full-suite/UI/MCP and publication requirements before review.
